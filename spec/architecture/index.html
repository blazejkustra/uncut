Uncut architecture

Electron UI, a TypeScript server built with Effect, and a Rust media core (D11). One edit engine serves both the user and the agent, so every change is checked, attributed and undoable the same way (D6, D7, D12).

Four flows

1. Open a project

  1. The renderer asks the server to open Launch video.uncut/.
  2. The server reads project.json, validates it, opens history.db and loads module manifests.
  3. The media core probes media, builds missing proxies, waveforms and thumbnails into .cache/ in the background.
  4. The server sends a snapshot with its revision. The UI draws the timeline right away and fills in thumbnails as jobs finish.

2. Scrub and play

  1. The playhead lives in the renderer. Scrubbing never round-trips through the server.
  2. The graphics layer calls render(t) in the page for text, components and transitions.
  3. Footage plays in Chromium <video> elements decoded by VideoToolbox, straight from the original files. One element per visible clip; a transition shows two.
  4. Audio plays from the media core's engine, so meters and ducking match export.

3. The agent edits

  1. You send a prompt. The orchestrator starts a turn with the provider adapter (for example claude), adding the note about your manual edits.
  2. The agent reads the project, analyzes media and looks at frames through Uncut's MCP tools.
  3. It calls timeline_edit with the revision it saw. The edit engine checks for conflicts with your newer edits, validates and commits.
  4. The change lands in history.db with the turn id, project.json is written, and the UI updates and fills the turn card. "Undo turn" removes the whole turn.

4. Export

  1. The export dialog starts a job on the server.
  2. The footage is cut and crossfaded from the original files with the same frame maths as the preview, and an offscreen window renders the same HTML graphics as the preview.
  3. The compositor layers them and the encoder writes H.264. The audio engine mixes, then normalises to the LUFS target.
  4. Progress streams to the UI. When it's done, Finder opens on the file.

Decided by spike A

Measured in Electron 44 on an M4 Pro with the user's own drone clip (3840×2160 HEVC Main 10, 59.94 fps, 5.6 minutes, 3.6 GB):

  • Preview decodes in Chromium. A <video> element plays the original at 60 fps with 0 dropped frames and seeks in 30 ms (median of 40). Two 4K streams at once, as in a crossfade, hold 55 fps. Scrubbing in the editor settles in about 100 ms. No proxies and no Rust on the preview path.
  • Export uses the same timeline maths. Shots and crossfades are cut from the originals by ffmpeg with VideoToolbox; text is rendered by Chromium from the same HTML as the preview. Exported frames match the source at SSIM 0.97 to 0.998, and a 35 s 4K export takes about 35 s.
  • The media core becomes a helper process for analysis, waveforms and the audio engine, started when needed. Smelter wasn't evaluated: the Chromium path passed, so there was nothing left for it to de-risk.

Playback engine (D311)

A <video> per clip only starts seeking when the playhead reaches its cut, so dense cuts (0.2 to 0.5 s) stalled, froze or drifted. While playing, the preview now demuxes the files itself (mediabunny) and decodes with WebCodecs ahead of the playhead: each clip on screen and the next ones within 2.5 s get a decoder filling a short frame queue, the soonest first, and the compositor draws the frame the playback clock asks for. Clips it draws are heard through the mix's own <audio>. Files WebCodecs can't take (ProRes, HDR, containers mediabunny can't read), looped clips, shuttling and scrubbing stay on the <video> and the scrub cache (D221).
